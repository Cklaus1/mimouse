- Clipboard (and therefore P3 files) is not implemented on macOS. (P2)

- GNOME 50: removing the last client and adding one (e.g. re-pairing) recreates the capture session, so the approval dialog appears again. Keeping the session alive with no barriers would avoid it. (P3)

- layer-shell `update_windows` (`input-capture/src/layer_shell.rs:587`): `active_windows.clear()` on an output change leaves `focused` on a dropped window while the grab may be held; no End is emitted. `grab` (`:464`) still unwraps `focused`. (P3, from K2)

- `authorized_keys` is a `std::sync::RwLock` with `.expect("lock")` at every use (`src/service.rs:70`, `src/listen.rs:70`, `src/clipboard/transport.rs:85`, `src/clipboard/mod.rs:172`). (P3, from G1)

- libei/GNOME (K4, B13): startup with 2+ clients should give one portal session and one dialog; integrator smoke checks the journal for a single `creating input capture session`. A truly long-lived session (re-arming barriers) is impossible: mutter AddBarrier needs INIT state. (P2, from K4)
- webrtc-dtls 0.12.0 `src/conn/mod.rs:390-405`: the DTLS reader breaks only on `ErrAlertFatalOrClose`; any other recv error (e.g. `ErrBufferClosed`) spins at 100% CPU until the DTLSConn is dropped. MiMouse avoids it by closing DTLS (10 s) before UDP idle eviction (30 s); worth an upstream fix. (P2, from N2)
- `MiMouseListener::get_certificate_fingerprint` recomputes the fingerprint from DTLS state on every Ack; store it with each conn in `conns` (also serves B2, close conns on key revocation). (P3, from N2)
- After `request_port_change`, conns on the old socket linger until PEER_IDLE_TIMEOUT (10 s); the service could close them right away. (P3, from N2)
- Vendored webrtc-util tests are not in CI: add `exclude = ["vendor/webrtc-util"]` to the root workspace and run `cargo test --manifest-path vendor/webrtc-util/Cargo.toml --lib conn::` (pulls criterion/tokio-test dev-deps). (P3, from N2)
- The release workflow publishes no checksums (`.github/workflows/release.yml`); unsigned binaries (D6) leave users nothing to verify a download against. Candidate for R1: a `SHA256SUMS` asset. (P2, from W1)

Costs one reconnect per start; cause not traced (megapc pongs during emulation/clipboard startup?). (P2, from N3 smoke)
- No CLI to clear a pin: a peer with a legitimately new certificate needs a hand edit of `fingerprint` or a re-pair (`mimouse cli unpin <id>` candidate). After the edit, reconnect waits for the backoff (16 s observed). (P3, from N3)
